The user wants the local model's weights changed to achieve this goal:

{goal}

Use the `model_weights` tool to do it yourself. Work in these stages and report what you actually measured.

1. Orient. Call `status` (free) to see earlier experiments and edits; do not repeat an edit that already failed. Call `map` once for the layer and head counts, then `analyze` once (no arguments) for the atlas: which layers matter most, which heads are induction/copy heads, and what the busiest neurons write. Use it to pick where to look; it is a lead, not proof.
2. Turn the goal into a measurable behaviour. Decide what a failing answer looks like and what a good one looks like, and how to check it (`required` / `forbidden` substrings, token-limit hits, repetition). If the user has real failing transcripts, prefer them: ask for them or read them from the workspace or session logs. Otherwise write prompts that provoke the behaviour, and say that they are synthetic.
3. Create an experiment with `experiment` and a budget of about 12 model runs. Every generate, direction, attribute and try spends one run; edit is free.
4. Reproduce the problem. `generate` on 12-16 prompts that provoke it and look at the numbers (and `tail` for a few answers). If you cannot reproduce it, stop and tell the user; do not edit a model that does not show the problem.
5. Find what to change. Run `attribute` with `cases` (conversations ending in a real unwanted answer), `wanted` (the same prompts ending in a good answer) and `neutral` (4-8 ordinary answers that must stay unchanged). For repetition use `focus: repeats`. Read `agreement` (share of cases the component helps; ignore low values), `promotes`/`suppresses` on neurons and `induction` on heads, and say in plain words why you pick each candidate. A neuron whose tokens have nothing to do with the behaviour is probably a generally important one: leave it alone.
6. Test before writing. Use `try` with `method: scale` and `{layer, heads|neurons, scale}` changes (on mixture-of-experts models `{layer, experts: [...], scale}` or `{layer, shared_expert: true, scale}`) at several `doses` with `neutral` answers. Keep a candidate only if the loss on `cases` drops while neutral drift stays near zero. If nothing qualifies, say so; a negative result is a valid outcome. `direction` plus `edit` with the default method is the alternative when no small component set works.
7. Write and judge. `edit` the best candidate (on a 4-bit model a refused edit means the change is smaller than the rounding noise: use larger components or tell the user to use an 8-bit copy). Then `evaluate` on at least 8 held-out prompts the experiment never saw, ideally 16-32, written after you picked the edit. Run `evaluate` once per edit; do not tune the edit on the held-out prompts. An evaluation also fails when the edit raises loss on general probe text by more than 5%; report that `quality` line.
8. Report. State the goal, what you measured before and after, which components you changed and why, whether the edit passed (wins, losses, ties, p), and the limits (model size, number of prompts, synthetic data). Only the user can adopt an edit: tell them to run `/weights promote NAME` if it passed, or `/weights open` to see the charts. Never claim an edit works unless `evaluate` passed.

Every `model_weights` call except `status` asks the user for approval. Keep calls few and purposeful.
